## مورد ۱ — UI موفقیت پیامک/اطلاع‌رسانی را اعلام می‌کند، ولی عملیاتی وجود ندارد
**اولویت P1 | قطعی**

**محل:** BookingVM:851–857 ، BookingService:72–76 ، DetailVM:179–181, 184–187 ، `src/Animora.Desktop/Pages/Appointments/BookingDetailView.axaml:157–160` ، CalendarVM:1105–1106

**واقعیت کد:** چند پیام موفقیت بدون پشتوانهٔ اجرایی:
- ثبت نوبت می‌گوید «پیامک تأیید ارسال شد».
- فرمان پیامکِ جزئیات فقط `toast` نشان می‌دهد.
- لغو می‌گوید «به مالک اطلاع داده شد».
- timeline ارسال پیامک را به‌صورت متن ثابت نشان می‌دهد.
- تنظیمات ارسال خودکار یادآوری را وعده می‌دهد.
اما درخواست ثبت به دستوری تبدیل می‌شود که پارامترهای پیامک ندارد (`BookAppointmentCommand` فیلد SMS ندارد) و هیچ مسیر ارسال/صف پیامک یا نتیجهٔ تحویل وجود ندارد.
**نکتهٔ موجود در کد بک‌اند:** در `Animora.Client.Services/Vaccination/SmsTemplateRenderer` فقط رندر متن پیامک هست و صریحاً **no delivery**. یعنی لایهٔ تحویل پیامک در محصول فعلی وجود ندارد (و به سرور/فاز آینده مربوط است → خارج از حوزهٔ رفعِ «ارسال واقعی»).

**کار لازم (صداقت، نه ساختِ سامانهٔ پیامک):**
1. همهٔ پیام‌هایی که «ارسال شد/اطلاع داده شد» را ادعا می‌کنند به زبان صادقانه تغییر بده: مثلاً «درخواست یادآوری ثبت شد» یا «در حالت آفلاین، پیامک ارسال نمی‌شود». هیچ toast نباید ارسالِ قطعی را ادعا کند.
2. مفاهیم «ثبت درخواست / صف‌شدن / ارسال / تحویل» را از هم جدا کن؛ تا وقتی لایهٔ تحویل نیست، فقط تا مرحلهٔ «ثبت درخواست» را به کاربر بگو.
3. متن ثابتِ timeline که ارسال پیامک را قطعی نشان می‌دهد، به وضعیت واقعی (ثبت‌شده/نامشخص) تغییر کند.
4. اگر `SendSms/SendReminder` در فرم هست ولی اثری ندارد: یا این سوییچ‌ها را به یک «نیت ثبت‌شده» واقعی (ذخیره در نوبت، اگر دامنه پشتیبانی می‌کند) وصل کن، یا در UI صریحاً به‌عنوان «برنامه‌ریزی‌شده (بدون ارسال آفلاین)» برچسب بزن. (هماهنگی با TASK-01 مورد ۲ که فیلدهای SMS در ویرایش دور ریخته می‌شدند.)

**معیار پذیرش:** هیچ پیام UI ادعای ارسالِ انجام‌نشده نکند؛ وضعیت واقعی (ثبت درخواست / بدون ارسال آفلاین) صادقانه بیان شود.

## مورد ۱۱ — تنظیمات synchronous و مسیر خرابی/اعتبارسنجی ناقص
**اولویت P2 | قطعی** *(بخش نوشتن/اعتبارسنجی؛ بخش دسترسی در مورد ۲ همین تسک)*

**محل:** SettingsService:36–45, 48–64, 101–139

**واقعیت کد (چند مسئله در یک مرز ذخیره‌سازی):**
- متدهای `Task`دار، `ReadAllText`/`WriteAllText` **synchronous** را زیر lock اجرا می‌کنند (توقف UI روی دیسک کند).
- فایل خراب/غیرقابل‌خواندن بدون log/هشدار به default تبدیل می‌شود؛ نوشتن بعدی می‌تواند تنظیمات قبلی را با default جایگزین کند.
- `Normalize()` فقط Sms و null بودن collection را تا حدی مدیریت می‌کند؛ اعتبار اعضای نوع سفارشی/شناسهٔ تکراری/رنگ/enum/مدت کامل نیست. clamp مدت مضرب پنج را تضمین نمی‌کند.
- temp filename ثابت است و lock فقط داخل همین process محافظت می‌کند؛ cache با ویرایش خارجی فایل reconcile نمی‌شود؛ schema version برای تحول فایل وجود ندارد.
- **مثبت:** استفاده از temp + rename خوب است ولی به‌تنهایی crash-recovery/چندprocessی را کامل نمی‌کند.

**کار لازم:**
1. I/O فایل را async واقعی کن (یا حداقل خارج از l/ock بلندمدت و بدون بلاک UI thread).
2. فایل خراب را log/هشدار بده و از جایگزینی خاموشِ تنظیمات معتبر با default جلوگیری کن.
3. `Normalize()` را کامل کن: اعتبار شناسهٔ یکتا، رنگ، enum، مدت (مضرب پنج)، و رد اعضای نامعتبر.
4. `schema version` به فایل اضافه کن تا migration آینده ممکن باشد.
5. temp filename یکتا کن.

**معیار پذیرش:** نوشتن/خواندن تنظیمات UI را بلاک نکند، فایل خراب بی‌صدا دادهٔ معتبر را نابود نکند، و ورودی نامعتبر رد شود.

## مورد ۱ — async بودن مسیر، اجرای SQL خارج از UI thread را تضمین نمی‌کند
**اولویت P1/P2 کارایی | ریسک فنی معتبر؛ شدت نیازمند اندازه‌گیری**

**محل:** CalendarVM:292–301 ، QueryService:15–23 ، `src/Animora.Application/Dispatch/Dispatcher.cs:36–52` ، SQLQueries:24–42

**واقعیت کد:** `Task.Yield()` فقط ادامهٔ کار را عقب می‌اندازد؛ آن را به worker thread منتقل نمی‌کند. dispatcher همان pipeline را روی context فراخواننده اجرا می‌کند. در provider SQLite، صرف استفاده از APIهای async به معنی I/O واقعاً غیرمسدودکننده نیست. مرز صریح اجرای query روی worker در این مسیر دیده نمی‌شود ⇒ SQL سنگین/lock wait می‌تواند UI را متوقف کند. comment مربوط به mock/`Task.FromResult` هم قدیمی شده.

**کار لازم:**
1. یک مرز صریح اجرای query روی worker thread تضمین کن (مثلاً خواندن‌های سنگین از طریق `Task.Run`/زمان‌بند مناسب خارج از UI thread اجرا شوند — مطابق الگوی پذیرفته‌شده در پروژه؛ به `PERFORMANCE.md` بخش مربوط به thread/responsiveness نگاه کن).
2. `Task.Yield()` را که نقش واقعی offload ندارد با مرز درست جایگزین کن.
3. comment قدیمیِ mock را اصلاح کن (هماهنگ با مورد ۱۳).
- **اندازه‌گیری نکن/ادعای عدد نساز؛ فقط مرز اجرای درست را بگذار.**

**معیار پذیرش:** خواندن‌های سنگین نوبت‌ها روی UI thread اجرا نشوند؛ مسیر thread صریح و هماهنگ با استاندارد پروژه باشد.

- [ ] انجام شد

## مورد ۲ — هر انتخاب در فرم، چند query سریالی و غیرضروری می‌زند
**اولویت P2 | قطعی**

**محل:** BookingVM:330–345, 496–502

**واقعیت کد:** هر `ReloadAvailableAsync()` شامل: دریافت slotها + دریافت conflictها (حالت زمانی) + یک busy-count برای **هر پزشک** + شمارندهٔ کل تقویم ماهانه + rebuild کامل فرم است (≈ تعداد پزشکان + ۳ عملیات). تغییر فقط ساعت شروع، busy-count همهٔ پزشکان و count ماه را دوباره می‌خواند با اینکه ورودی‌شان تغییر نکرده.

**کار لازم:**

2. یک بودجهٔ query مشخص برای هر تعامل تعریف کن و فقط بخش‌های متأثر را refresh کن (هماهنگ با latest-wins از TASK-04 مورد ۲).

**معیار پذیرش:** تغییر یک ورودی فقط کوئری‌های وابسته به همان ورودی را trigger کند؛ تعداد SQL هر تعامل کاهش یابد.

## مورد ۶ — بسته‌بندی overlap در بدترین حالت درجه‌دو است و عرض کارت حداقل کاربردی ندارد
**اولویت P2 | قطعی از الگوریتم**

**محل:** CalendarVM:702–759 ، `TimeGridEventsPanel.cs:57–61`

**واقعیت کد:** برای هر نوبت `lanes.FindIndex(...)` روی laneهای موجود اسکن می‌کند ⇒ در خوشهٔ پرتداخل O(n²). عرض کارت = `عرض ستون / تعداد lane − ۸` که می‌تواند به صفر برسد ⇒ کارت‌های بسیار باریک/غیرقابل‌تعامل.

**کار لازم:**
1. الگوریتم lane-assignment را به روشِ کاراتر (مثلاً sweep-line با مرتب‌سازی بر شروع و آزادسازی laneهای تمام‌شده) تبدیل کن تا از O(n²) خارج شود.
2. یک **حداقل عرض کاربردی** برای کارت بگذار و یک مسیر overflow (مثلاً «+N بیشتر») برای خوشه‌های خیلی متراکم تعریف کن تا کارت‌ها به صفر نرسند.

**معیار پذیرش:** خوشه‌های پرتداخل هم سریع layout شوند و کارت‌ها خوانا/قابل‌تعامل بمانند.

- [ ] انجام شد
